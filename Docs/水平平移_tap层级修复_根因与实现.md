# 水平平移：tap 层级修复（第四版）

日期：2026-11-23
状态：已编译、测试通过，**待真机 FCP 验证**

## 一、为什么第三版（搬轴）失败

第三版参考 Mos 把垂直增量 Δ1 搬到水平轴 Δ2，同时改 flags 为 Shift。真机仍无平移。

根因：**对 FCP 而言，搬轴是方向性错误。**

用户实测的真实 Shift+滚轮事件结构（诊断探针抓取）：

| 字段 | 真实 Shift+滚轮 |
|---|---|
| flags | `0x20002` |
| Δ1（垂直轴） | 有值（如 -3） |
| Δ2（水平轴） | 0 |
| phase | 0 |

FCP 是靠「Shift 标志 **+ 垂直轴增量 Δ1**」自己内部转换成时间线水平平移的——增量留在垂直轴是必要条件。第三版把 Δ1 清零、搬到 Δ2，等于 FCP 认出了 Shift 却拿不到它需要的增量，自然不动。

> 注：Mos 的搬轴方案面向 Safari/Chrome 等标准应用（它们直接读水平轴 Δ2）。FCP 的时间线平移是它自定义的交互，机制不同，不能照搬。

## 二、为什么前两版（只改 flags）时灵时不灵

事件 tap 挂在 `.cgSessionEventTap` + `.headInsertEventTap`——位于系统「注释层」之前、且排在所有 tap 最前面。

在此层改写 flags 后，下层仍可能用**物理按键的真实状态**（用户实际按的是 Option）重新注释事件，导致改写后的 Shift 时被覆盖、时不被覆盖。这正是「能用一下，再用又不能」的典型成因。

## 三、本版改动

1. **撤销搬轴**：只改 flags（Option/Control → Shift，高低位同步），**完整保留 Δ1 / Δ2 / 相位 / 时间戳**，使事件结构与真实 Shift+滚轮逐字段一致。
2. **更换 tap 落点**：
   - 层级：`.cgSessionEventTap` → `.cgAnnotatedSessionEventTap`（AppKit 构造 NSEvent 前的最后一层）
   - 位置：`.headInsertEventTap` → `.tailAppendEventTap`（排在所有 tap 之后，改写直达应用）

   该落点与成熟滚轮工具 Mos 一致。

## 五、若本版仍失败

不再修改事件改写路径。剩余可靠方案是与缩放同一套机制——**AX 驱动**：

- 缩放功能从第一版起始终稳定，因为它不走事件改写，而是用 AX 点击 FCP 的「放大/缩小」菜单项。
- 平移可改用同样的 AX 路径：枚举并触发 FCP 的平移相关菜单项/快捷键，或直接操作时间线滚动条。
- 这需要改变产品交互定义（从「滚轮修饰键映射」变为「按键触发平移」），需用户先确认方向。
